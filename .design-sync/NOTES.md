# design-sync notes — Maneuver 2026 UI

## Repo shape

This repo is an app (Vite + React + shadcn/ui), not a published component library — there's no `dist/` build that exports the UI primitives as a package. The sync targets only `src/core/components/ui/` (shadcn primitives), via the **synth-entry** fallback (no real `.d.ts` tree — weaker prop contracts than a real build would give).

- `src/components/ui/` (top-level) is empty — a leftover/decoy dir. The real primitives live at `src/core/components/ui/`.
- To reach `resolvePackage`'s synth-entry path (needed because `node_modules/maneuver-2026` doesn't exist — this repo isn't installed as its own dependency), `package-build.mjs` is invoked with `--entry ./.design-sync/no-dist-marker.ts` — a **deliberately nonexistent path**. Its dirname (`.design-sync/`) walks up to the repo root `package.json` (has a `name`), which correctly sets `PKG_DIR` = repo root; the nonexistent file itself makes `resolveDistEntry` return `null` (soft-fail), triggering the synth-from-`cfg.srcDir` fallback. This is intentional, not a bug — keep this exact flag on every rebuild until this repo ever ships a real component-library build.

## CSS: compiled, not raw

`cfg.cssEntry` points at `.design-sync/compiled/app.css`, a **copy of the Vite-compiled Tailwind output** (`dist/assets/index-*.css` after `npm run build`), not `src/index.css` directly. Tailwind v4's `@import "tailwindcss"` in the raw source only pulls in the engine's base layer — the actual utility classes (`bg-primary`, `flex`, etc.) are JIT-generated by the Vite plugin at build time and only exist in the compiled output.

**`.design-sync/compiled/` is gitignored** (regenerated, matches the durable-set rule). Before every build/re-sync:
```
npm run build
cp dist/assets/index-*.css .design-sync/compiled/app.css
```
The exact hashed filename changes every build — always re-copy, don't hardcode it in config.

## Fonts

`cfg.extraFonts: ["src/index.css"]` — the compiled CSS's `@font-face` `url()`s point at Vite's hashed `dist/assets/*.ttf` paths, which aren't copied anywhere near `.design-sync/compiled/app.css`, so the scrape drops them as dead. Pointing `extraFonts` at the real source `src/index.css` (correct relative paths to `src/assets/fonts/*.ttf`) harvests the real Titillium Web files correctly.

**Known render warn — accepted, not chased**: `[FONT_MISSING] "Avenir"`. It's a macOS system-font fallback in the CSS `font-family` stack (`"Titillium Web", system-ui, Avenir, ...`), not a real shipped brand font — no license to bundle it, and it's meant to fall through to the OS. Accepted substitute (system fonts), per user OK on 2026-07-27.

## Excluded components

`cfg.componentSrcMap`: `MobileOverlay` and `SwipeToOpenDetector` (from `sidebar/touch-handlers.tsx`) are excluded — internal sidebar implementation details, never re-exported from the public `sidebar.tsx` barrel or `src/components/index.ts`.

## Preview scope (family-level only)

The synth-entry scan surfaces **146 individual components** (down from an initial 148 after the exclusions above) because shadcn compound components export every sub-part separately (`Card`, `CardHeader`, `CardTitle`, `CardContent`, `CardFooter` = 5 exports). Per user decision on 2026-07-27: only the ~30 real component **families** get authored, composed previews (Card demonstrates its full header/title/content/footer composition, Dialog shows the open dialog, etc.). The ~116 sub-part exports still ship fully functional with real `.d.ts`/`.prompt.md` (accurate props for the design agent) but keep the floor card — authorable incrementally on a future re-sync.

## Known render warns (floor cards, not failures)

`[RENDER_BLANK]` on all unauthored sub-part floor cards (Avatar, Badge, Button, CardHeader, Checkbox, DropdownMenuLabel, DropdownMenuSeparator, Kbd, KbdGroup, Progress, SelectSeparator, Sidebar* subparts, TableCaption, TableCell, TableHead, etc.) is the typographic floor card's PNG being <5KB — expected for every component not yet authored. Not a bug. Re-syncs should check new warns against this list; a warn that shows up on a component we DID author is real and needs chasing.

## Preview authoring: no external network URLs

`Avatar`'s `WithImage` cell was originally authored with an external Unsplash `src` URL — it rendered fine in our local Playwright capture (which has network access) but would very likely render broken in claude.ai/design's actual render sandbox (external fetches are commonly blocked by CSP there). Fixed by swapping to an inline `data:image/svg+xml;base64,...` placeholder. **Any future preview needing a photographic placeholder should use an inline data URI, never an external URL** — checked this wasn't repeated elsewhere in this run's previews.

## Toaster: left on the floor card (tooling limitation, not a bug)

`package-capture.mjs` calls `page.clock.setFixedTime(...)` on the Playwright page, which installs a frozen fake clock — `setTimeout`/timer callbacks scheduled after that never fire on their own. `sonner` (the `Toaster`/`toast()` library this wraps) defers actually adding a toast to its rendered list via a bare `setTimeout(() => flushSync(...))` inside its internal store subscription (see `node_modules/sonner/dist/index.mjs`) — so a toast triggered in a preview's `useEffect` never makes it into the DOM before the screenshot is taken, no matter how the preview is written. (`SortableList`'s framer-motion mount animation had the same frozen-clock exposure but was fixable — `MotionConfig reducedMotion="always"` bypasses the animation loop instead of depending on it ticking; sonner has no equivalent escape hatch we could find.)

Tried and ruled out: `useLayoutEffect` instead of `useEffect` (doesn't change sonner's own internal `setTimeout`), CSS `prefers-reduced-motion` (sonner respects it for transition *duration*, but the toast still isn't in the DOM at all pre-timer). No `cfg.overrides` skip was needed — the component simply has no authored preview, so it renders its honest floor card, which is correct per the family-level-only scope decision, not a defect.

**If revisited later**: the fix would need to happen in the capture tool itself (don't freeze the clock, or advance it after each `page.goto`) — out of scope for a per-repo config change.

## SortableList: also left on the floor card (different mechanism, same practical outcome)

`SortableListItem` (in `sortable-list.tsx`) unconditionally wraps its content in `motion.div`/`Reorder.Item` with `initial={{opacity:0}}` → `animate={{opacity:1,...}}` from `motion/react` (framer-motion). First attempted fix: wrap the preview in `<MotionConfig reducedMotion="always">` to skip the animation and jump straight to the settled state. This compiled correctly but had **zero effect** at runtime — screenshot still totally blank.

Root cause: `SortableList`/`SortableListItem` are imported from `"maneuver-2026"` (resolved to `window.ManeuverUI.*` — the REAL implementation lives inside `_ds_bundle.js`, which has its OWN esbuild-bundled copy of `motion/react`). The preview file's `import { MotionConfig } from "motion/react"` is a bare npm import that is NOT routed through the DS bundle's shim — esbuild bundles a **second, independent copy** of `motion/react` directly into `_preview/SortableList.js`. Two separate module instances means two separate `MotionConfigContext` objects (`createContext()` is called twice) — a `<MotionConfig>` provider from the preview's copy has no effect on context consumers reading from the DS bundle's copy. Classic dual-package-instance hazard, not fixable by importing "more correctly" from the preview side since `motion/react` isn't (and shouldn't be) re-exported from the DS's own surface. This is likely compounded by (or possibly moot given) the same frozen-clock issue above.

**If revisited later**: no config-level fix exists for this class of problem in the current tool — would need either the DS to expose its own animation-config escape hatch, or a capture-tool feature to inject props into a real (non-isolated) instance of a third-party context provider. Out of scope here.

## Grid-display overrides (cardMode)

The final validate pass flagged 9 authored components as `[GRID_OVERFLOW]` — overlay/portal components whose open content escapes a grid cell (`AlertDialog`, `Dialog`, `DropdownMenu`, `Popover`, `Select`, `Sheet`, `Tooltip` → `cardMode: "single"` with an explicit `primaryStory`) or that render wider than a grid column (`Alert`, `Skeleton` → `cardMode: "column"`). All 9 overrides are in `cfg.overrides` in `config.json`. Applied via a *targeted* `preview-rebuild.mjs` batch (not a full rebuild) — per the skill, `cardMode` changes are presentation-only and exempt from re-triggering the check, so no re-validate was run; visual correctness was confirmed by re-reading each affected screenshot.

## Re-sync risks

- **`.design-sync/compiled/app.css` must be regenerated before every build** (see CSS section) — it's gitignored and machine/build-specific (hashed filename). A stale or missing copy silently produces an unstyled or `[CSS_PLACEHOLDER]` bundle.
- The synth-entry `--entry ./.design-sync/no-dist-marker.ts` flag is load-bearing (see Repo shape) — dropping it breaks `PKG_DIR` resolution against `node_modules/maneuver-2026` (ENOENT).
- No real `.d.ts` build exists for `src/core/components/ui/` — prop contracts come from ts-morph's structural read of the `.tsx` source directly. If this repo ever adds a real build step for the UI kit (e.g. publishing it as its own package), switch away from synth-entry and drop `no-dist-marker.ts` + `extraFonts`/`cssEntry` workarounds — a real `dist/` + `.d.ts` will give stronger contracts.
- Tokens: 2 CSS custom properties referenced but undefined (below the warn threshold) — not chased; harmless unless it grows.
